阅读范围与连线说明 · CLI → 模型加载 → KV Cache → Scheduler → Ready → HTTP
基于 vLLM v0.25.1（752a3a5044）。与运行树采用同一主线：单 API Server、TP/PP/DP/CP=1、显式 MultiprocExecutor、普通 Full Causal Self-Attention Llama / DefaultModelLoader、未量化、NVIDIA / Eager / FlashAttention、Runner V2（vllm/v1/worker/gpu/model_runner.py）。明确设置 VLLM_USE_V2_MODEL_RUNNER=1；同步调度、max_concurrent_batches=1、开启 Prefix Cache、自动 KV 显存预算，无投机解码 / KV Connector / LoRA / 跨层 packed 存储。单卡采用 MultiprocExecutor 是显式选择，不是默认部署结论。
从 CLI 发起位置展开：Process.start 下接子进程入口，MQ 发送下接 Worker 的接收片段。虚线代表执行上下文切换，不是 Python 同步调用；父进程与子进程仍并发，只有标出的等待点建立先后约束。实线表示同一上下文内的调用或代码块归属；灰色节点是条件、赋值或 yield / context 恢复，不是虚构的函数。
函数名跳转 GitHub 调用点，“实现”跳转函数定义；上下文节点链接入口，状态节点链接对应语句。“交接”定位接收方，“关联”定位相关节点。兄弟节点按源码顺序阅读，但带并发、条件、yield 的节点不能视作简单串行。
模型构造先于正式 KV 绑定。V2 初始 profile_run 使用 skip_attn=True；v0.25.1 的 profile_cudagraph_memory() 仅返回 0，没有 V1 的临时 KV 绑定流程。页面保留少量 Graph / 编译条件节点以说明跳过位置，但当前 Eager 主线不执行这些分支。正式绑定后，warmup_kernels 通过 Worker 执行模拟请求并清理；再完成 Ready 与 HTTP serving。Worker READY、EngineCoreReadyResponse 和 handshake READY 是不同信号。日志、异常路径、第三方库内部不逐项展开；不展开首个用户请求。全部样式、脚本与数据内嵌，文件可独立分享；打开 GitHub 链接时才需要网络。
